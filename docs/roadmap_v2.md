## The right way to evolve the working solver

The cleanest path is to treat the current OpenSpiel + PokerKit wrapper as the “ground-truth game interface,” and add abstraction layers on top of it rather than replacing or mutating the actual game. That preserves the working solver and lets you progressively add the poker-specific tricks you care about.

### Progress so far

- The wrapper-based OpenSpiel game path is working as the underlying solver interface.
- We have a stable local action-space flow that keeps PokerKit legal actions intact while filtering or abstracting at the reporting boundary.
- We can extract valid actor states and sample deeper-node policy snapshots from real game states.
- We have explicit validation of compact hand labels and canonical preflop grouping.
- We have a clean reporting shape for the compact range export: hand class + compact policy summary, without raw action-history noise.
- We can add convergence visibility without modifying the solver itself by measuring checkpoint-to-checkpoint policy stability.

This is the core “monitoring layer” we want before making larger algorithmic changes.

The ladder is:

1. Solve the real game with the working wrapper
2. Add an action abstraction layer
3. Add infoset bucketing
4. Add preflop range restrictions / priors
5. Only then consider solver variant changes

## 1) Reducing no-limit bet sizes per street

This is usually not a “different game” problem; it is an abstraction problem.

### Recommended pattern
Keep PokerKit legal actions available, but map them to a smaller abstract action set before solving or before policy export.

For example, on a no-limit street:

- check / call
- bet small
- bet medium
- bet large
- all-in
- raise small
- raise large

Street-specific examples:

- preflop: {check, call, 2x, 4x, all-in}
- flop: {check, call, 0.5 pot, 1 pot, all-in}
- turn / river: similar, with maybe fewer options

### Why this is the right place
If you directly change the raw legal actions generated by PokerKit, you risk breaking the game contract and the solver path itself. Better is:

- PokerKit still produces the real action list
- a wrapper maps those actions into abstract actions
- the solver uses the reduced abstract action space
- policy export maps abstract actions back to actual PokerKit actions

This gives you the “don’t break the action space” goal you wanted.

### Important caveat
This is not just a cosmetic filter. You are effectively solving a reduced game, not the exact game. That is normal and common in poker solvers. The key is to keep the abstraction explicit and consistent across training and gameplay.

## 2) ~~Is external sampling MCCFR a different solver we need to support?~~ DONE! (use solver=external, outcome)

Not really a different game contract — it is a different algorithm choice.

### In OpenSpiel terms
You are already in the right place with:

- ExternalSamplingMCCFRSolver

This is a valid solver for the same game model. The main difference is algorithmic:

- full CFR / standard CFR: updates all actions on each traversal
- external sampling: samples trajectories and updates only the sampled branch
- outcome: much faster, less memory, but noisier estimate

### Practical answer
You do not need a separate support path for “different game support” just because you switch from full CFR to external sampling. You keep the same PokerKit/OpenSpiel game and swap the solver object.

So the real question is:

- do you need exact regret updates or a fast approximation?
- if you want cheap iteration runs, external sampling is ideal
- if you want more stable convergence, full CFR is more faithful

For your use case, external sampling is perfectly reasonable as long as you measure policy quality by:
- valid action set
- normalized probability sum
- behavior stability over time

## 3) Hand + board strength bucketing

This is one of the most important poker-specific abstractions.

### The idea
Instead of solving on exact hand identities, solve on a bucketed infoset representation. Example:

- exact state: hole cards + board + pot + action history
- bucketed state: “premium pair on rainbow flop”, “draw-heavy board”, “weak top-pair”, etc.

Then the solver treats all hands in the same bucket as the same information state.

### Typical bucketing features
For a no-limit game, a good simple bucket key is something like:

- street
- board texture
- current hand strength
- equity vs. range
- number of outs / draw strength
- whether the hand is made or drawing
- action history and bet size context

### How it works in practice
At each acting point:

1. compute the exact hand / board combination
2. map it to a bucket id
3. use that bucket id as the infoset key in the policy lookup
4. keep the legal actions from PokerKit as the available actions

This lets the solver learn a policy over grouped states, which is how many poker solvers operate.

### Why it is a good fit here
The current wrapper is already giving you a working legal-action path. The bucket layer can sit directly above that:

- legal actions still come from PokerKit
- state-to-bucket translation happens before policy lookup or policy export
- final policy is converted back into real actions

This is much simpler and safer than redefining the whole game.

## 4) Adding known preflop ranges

This is also not a “new solver” issue; it is a range restriction / prior.

### The practical meaning
At the start of hand, each player has a set of allowed hole-card combinations before any action is taken.

Examples:

- Player 1: 20% opening range
- Player 2: 15% 3-bet range
- Player 1’s call ranges after open
- etc.

### How to add this
There are a few common ways:

#### Option A: restrict by legal root actions
Treat the root as a chance distribution over allowed hole cards and only include cards in each player’s range.

This is the most faithful if you want to enforce a fixed strategy context.

#### Option B: use a prior policy
At the root, assign each allowed action an initial distribution based on range membership.

For example:
- if hand is in the 3-bet range, actions like raise are allowed
- if not, call/fold becomes the only valid branch

#### Option C: filter during policy export
Train on the full game, then when extracting the final policy, only consider actions allowed by the player’s known range.

This is usually the easiest and least intrusive first step.

### For your stated goal
The phrase “adding known preflop ranges for each player over all possible preflop actions” maps naturally to:

- define range buckets by hand category
- define action legality by range
- then solve with those constraints

So you are not inventing a new architecture; you are constraining the game state distribution and policy space.

## The architecture I’d recommend

Use a layered abstraction:

1. PokerKit game object
   - exact legal actions
   - exact state transitions
   - real game rules

2. Action abstraction layer
   - compress raw legal bets into 2–5 abstract actions per street
   - map back to real actions when exporting

3. Infoset abstraction layer
   - hand + board bucketed to an infoset key
   - action history stays in the state context
   - legal actions remain from the real game

4. Range layer
   - preflop range restrictions or priors
   - per-player allowed hand categories

5. Solver
   - external sampling MCCFR, or full CFR if needed
   - same interface, different algorithm parameter

This keeps the solver path stable while adding the poker-specific modeling you care about.

---

## What should be done first

If the goal is to move from “working solver” to “useful poker solver,” I would do it in this order:

1. Action abstraction for no-limit
   - small set of bet sizes per street

2. Policy snapshot at valid actor states
   - confirm the reduced action space still gives valid distributions

3. Hand bucketing
   - first coarse bucket; don’t over-engineer it initially

4. Preflop ranges
   - start with static ranges, one by one, not a full dynamic model

5. Only then compare solver variants
   - standard CFR vs external sampling

## Addendum: convergence monitoring and policy stability

We do not need to change the solver to gain useful visibility into whether a run is learning or has effectively settled.

### Purpose
The goal is to answer: “is the policy still moving meaningfully, or has the run stabilized enough that additional iterations are marginal?”

### Standard monitoring signals
For each checkpoint, track:

- average-policy drift vs. the previous checkpoint
- dominant-action churn for the sampled infosets
- per-bucket action-mass stability
- average absolute regret or regret magnitude trend
- number of unique sampled infosets and how they evolve

### Why this matters here
For poker, true exploitability is ideal in a reduced or exact game, but in a large imperfect-information wrapper tree it is often too expensive or not cleanly available. In practice, the most useful signal is policy stability over time.

That means we can treat convergence as a monitoring layer:

- no solver modification
- no game-rule change
- just checkpoint comparison over the real run

### Operational rule of thumb
A run is probably “good enough for debugging” when:

- policy drift between checkpoints is small
- dominant actions stop flipping on the sampled infosets
- the same hand classes keep the same general action profile over repeated checkpoints
- deeper-node snapshots no longer show large oscillatory swings

### Practical recommendation
Add a lightweight checkpoint summary that prints:

- checkpoint iteration
- sampled infoset count
- average L1 delta from the prior checkpoint
- top 5 most volatile buckets by probability change
- dominant action for each sampled bucket

This is a reporting layer, not a solver redesign, and it gives us a real signal of whether the run is converging or still in a transient learning phase.

This is now part of the v2 roadmap as a first-class requirement for run diagnostics and for deciding when enough iterations have been spent.

## Bottom line

Yes, all of the goals you listed fit this exact architecture, but they should be handled as abstraction layers on top of the working PokerKit/OpenSpiel wrapper, not as custom replacements for the solver itself.

The key design principle is:

- keep the real game and legal action generation intact
- abstract only at the policy / infoset boundary
- solve on the reduced model
- map back to real actions when necessary

That is the standard way to do this in poker solvers, and it matches the direction you’ve already been pushing.
